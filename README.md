# まんまるよやく監視 v4 — 検証版

## 現状と重要な制約
- **実サイトへの連続アクセスはこの成果物では未検証です。** `config.json` の `site.verified` は `false`。動作検証が完了するまで変更しないでください。
- ユーザー提供のWork調査に基づき、多機能版 `gml_init`、画像 `timetable-o.gif`、`td.ok`、施設別の同一表、翌週リンクを実装。
- 施設コードが確認できた **8施設・19部屋** を登録。全施設網羅は未確認。
- 各部屋ごとに正常取得した日付のみ状態を更新し、未公開の日付やエラーになった部屋は維持。
- 初回の部屋別取得は基準値として保存し通知しない。次回以降、新規・再出現した空き枠を通知。
- 30分間隔での自動巡回は許可済みとの申告。負荷を見ながら間隔・対象数を調整。

## 導入前の検証
1. PythonとPlaywrightを導入し、`.env.example` をコピーして設定。トークンをGitに置かない。
2. `config.json` の対象を**まず1部屋**に絞り、Playwrightの画面操作・ページ送り・結果の日時対応を目視検証。
3. `#YYYY` の実option値、最初のエラー画面から多機能版への遷移、同じ表内の日付/状態行、時間帯の文字列を検証。これらはまだ未検証。
4. 1部屋の正常取得が確認できたら `site.verified=true` にし、`DRY_RUN=1` で動作確認。その後徐々に対象を増やす。
5. 公開期限が短い施設は `last_date` で明示され、未公開日は空きなしとして扱わない。
6. LINE公式アカウントでMessaging APIを有効にし、`LINE_CHANNEL_ACCESS_TOKEN` と `LINE_TO` を設定。
7. Dockerを利用するVPSに配置し、`docker compose up -d --build`、`docker compose logs -f` で監視。

## 注意
- ログイン、予約操作、空き枠クリックは行わない。
- `DRY_RUN=1` はLINEを送らずログ表示する。初回基準登録後の変化で通知テストを行う。
- 部屋単位で成功・失敗を分離。ただし通知送信とDB書込の厳密な原子性はなく、送信直後のプロセス異常時には重複通知の可能性がある。
- 現在の実装は1部屋ずつ検索するため、19部屋×最大約13週のアクセス負荷に注意。実際のアクセス数・所要時間を計測し、必要に応じてまとめて検索する方式へ変更。
- 結果表が未知の状態や想定外の構造の場合はその部屋を失敗扱いとし、過去の状態を保持。
- `runner.py` は完了後30分待機する方式。30分固定時刻での実行ではない。
